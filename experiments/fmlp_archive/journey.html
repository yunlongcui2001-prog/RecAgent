D17 2026-05-24 序列 padding 方向 = 左 pad（pad token 在前，真实 item 在后；不足 max_len=50 时左侧补 0） 论文 Eq.9：P(i_{t+1}|i_{1:t}) = e_i^T · F^L_t，用最后位置做预测。左 pad 保证最后位置永远是真实 item；右 pad 的话最后位置可能是 pad，hidden 无效。padding_idx=0 让 pad 的 item embedding 自动为零向量。
D18 ⚙️ 2026-05-24 修订 D11：dropout 0.5 → 0.2 D11 的 0.5 在第一轮全量训练中卡在 val_hr10=0.386（低于 GRU4Rec 0.4106，未达 D4）。反思：我们模型可学习"网络"只 24K 参数（97% 是 item embedding），dropout 0.5 等于关掉一半网络信号，对小网络过狠。BERT4Rec 在类似规模用 0.2，更合适小数据/小模型场景。论文从未明确 dropout rate（D9 禁查源码），故自主修订。
D19 ⚙️ 2026-05-24 负采样策略：从「排除整个 user 历史」改为「只排除当前 target」（经典 BPR）
D19 已撤销		 M4 显示 train_loss=0.04 vs val 早 plateau = 过拟合。原策略让模型从未"接触"过用户已交互 item 作为负，模型学到的"item 不像用户交互"是基于"从未见过"的伪信号；经典 BPR 允许采到 user 其他历史 item 作为负，loss 更难压到 0，泛化反而更好。论文 Eq.10 仅说"randomly sampled negative"，未约束排除集合，所以两种都符合 D9。
E3 推翻：HR@10 反降 2.3% / NDCG@10 -3.7% / MRR -4.0%。已回滚 data.py 到 E2 版本。
D20 ⚙️ 2026-05-25 修订 D16：FFN hidden_dim 64 → 256（4× expansion，Transformer 传统） E2 已是「dropout=0.2 + 排除 user 历史负采样」组合的局部最优 (HR@10=0.398)，但仍差 GRU4Rec/SASRec。E3 推翻"负采样是瓶颈"的假设。换"容量维度"试：当前 FFN 只 8K 参数（2×64×64），D16 我拍 d→d→d 是"轻量"先验；改 4d 后 FFN 容量 ×4（→ ~33K），总参数 24K→~70K，仍只占 item embed 的 9%，过拟合空间小。论文 Eq.8 未约束 hidden_dim，符合 D9。
E4 PARTIAL ⭐：HR@10 升至 0.4012（首次过 0.40），成为新 best baseline。
D21 ⚙️ 2026-05-25 修订 D 配置默认：num_blocks 2 → 4（更深） E4 验证"加容量"方向有效但增益仅 +0.7%，需要换维度继续推。论文 §6 消融提到 L=16 仍有增益（"with the increasing of the layer number, the performance of FMLP-Rec can be further improved. However, when the layer number achieves 16, the gain starts to become trivial"），说明 L=2 偏保守。改 L=4 双倍深度，每 block ~33K（FFN=256），加深后非 embed 参数 ~150K，仍只占总参 16%。
E5 PARTIAL ⭐⭐：HR@10=0.4133 (+3.0%) · 突破 GRU4Rec 双指标。
D22 ⚙️ 2026-05-25 optimizer Adam → AdamW，新增 weight_decay=1e-4 E5 train_loss=0.0615 仍偏低 + test_hr10=0.4133 与论文 SASRec 0.4696 差 12%，提示 over-fit 仍是瓶颈之一。AdamW 是 Adam 的 decoupled weight decay 变体（PyTorch 标准），1e-4 是工程常规起手。论文未明示 optimizer 是 Adam 还是 AdamW（仅写 "Adam"），weight_decay 默认 0；加上属于工程级正则补强，符合 D9（论文未明确即可自主）。

关于 dropout 的对话沉淀（用户问）： ① dropout 0.2 在 BERT4Rec / 推荐系统是默认值； ② 大语言模型（Llama）和现代 ViT 几乎不用 dropout（改用 weight decay 或 stochastic depth），但推荐系统因数据稀疏 + 模型小，dropout 仍主流； ③ LN（归一化）/ ReLU（激活）/ Dropout（正则化）是正交关注，不能互相替代； ④ 论文 §4.1 + Eq.7 明确 3 处用 dropout，但未指定 rate。

1.1 架构精规格

整体结构 = Embedding → ×L (Filter Block) → Prediction：

Embedding Layer
  E   = ItemEmbed(seq)        # R^{n×d}
  E_I = Dropout(LayerNorm(E + PosEmbed))    # n=50, d=64

Learnable Filter-enhanced Block × L  (L=2):
  Filter Layer:
    X_l   = FFT(F_l)              # 1D FFT along seq dim → C^{n×d}
    X_l~  = W ⊙ X_l               # W ∈ C^{n×d} 可学习复数滤波器（element-wise）
    F_l~  = iFFT(X_l~)            # → R^{n×d}
    F_l   = LayerNorm(F_l + Dropout(F_l~))     # skip + LN
  FFN:
    FFN(F_l) = (ReLU(F_l·W1 + b1)) · W2 + b2
    F_{l+1}  = LayerNorm(F_l + Dropout(FFN(F_l)))

Prediction Layer:
  score(i | seq_{1:t}) = e_i^T · F^L_t        # 点积匹配 item embedding

1.2 损失函数（关键！）

BPR-style pairwise rank loss，1:1 负采样（每个正样本随机配一个未交互过的负样本）：

L = -Σ_u Σ_t  log σ( score(i_{t+1} | seq_{1:t}) - score(i_{t+1}^- | seq_{1:t}) )

注意：训练时 1:1 负采样；评测时是 1:99 负采样（详见 1.4）。

1.4 数据预处理 & 评测协议

  • 5-core filter：去掉交互次数 < 5 的 user 和 item（迭代到稳定）
  • 按 user/session group + 时间升序排序 形成序列
  • Leave-one-out split：序列最后 1 个 = test，倒数第 2 个 = val，其余 = train
  • 评测：测试 item + 99 个用户未交互过的随机负样本一起 rank，算 HR@{1,5,10} + NDCG@{5,10} + MRR

阶段 2 — fmlp-rec/ 骨架设计 DRAFT · 待审

  • 目标：在不参考论文 repo（D9）的前提下，凭论文文本 + PyTorch Lightning 经验，设计一个最小但完整的项目骨架
  • 设计原则：
    • 核心创新（Filter Layer）独立文件，便于读、测、消融
    • Loss / Metric / Optimizer / Eval 流程集中在 LightningModule
    • 数据预处理与训练解耦（dataset 处理脚本一次跑完，训练只读处理后产物）
    • 带最小测试：FFT 可逆性、复数滤波器梯度流、负样本不污染正样本——这几个是 FFT-based 模型的常见踩坑点

2.3 已知的工程踩坑点（凭经验，预先标记）

  • 复数张量的 dropout：PyTorch 的 nn.Dropout 不支持复数 tensor。Filter Layer 内部如果想做 dropout，要在 iFFT 之后做（论文 Eq.7 正好如此）✓
  • FFT 的 batch 维：torch.fft.rfft 默认在最后一维做。我们的 tensor shape 是 (batch, seq=50, dim=64)，要在 dim=-2（seq 维）做 FFT，要么转置要么显式传 dim 参数
  • 实数 FFT vs 复数 FFT：rfft 输出 (n//2+1) 个复数频点，比 fft 省一半。论文说 W ∈ C^{n×d}，按理用 fft；但 rfft + 对应 irfft 数学等价且实数输入更快——决策：用 rfft/irfft，W 形状改为 (n//2+1, d) 复数
  • CPU MKL FFT 数值精度：CPU 上 FFT 误差比 GPU 稍大，iFFT(FFT(x)) ≈ x 测试要用 atol=1e-5 而非默认
  • 99-neg 评测集要缓存：每次评测重新采 99 个负样本会导致评测结果有方差，应该在 prepare_data 时一次性采好存盘

E3 — 实验点：负采样策略

假设去掉"排除 user 历史"后，模型被迫学到"用户已交互过的相似 item，也可能不是下一个 target"这种更细粒度的偏好——train_loss 不会那么快压到 0，泛化反而更好。
改前 (E2)neg 采样 = 排除整个 user 历史 · HR@10=0.398 · NDCG@10=0.254 · MRR=0.229 · train_loss=0.0421
改后 (E3)neg 采样 = 只排除当前 target（经典 BPR） · HR@10=0.389 · NDCG@10=0.245 · MRR=0.220 · train_loss=0.0967 · 122 epoch（best @112）· 用时 ~29 min
deltaHR@10 -2.3% · NDCG@10 -3.7% · MRR -4.0% · train_loss +130%
代码改动data.py · FMLPTrainDataset: 删 or neg in seen 过滤；__init__ 简化（不再为每 instance 存 seen 集合）
结论REJECTED 假设错了，全线 -2 ~ -4% 下滑。
验证的部分：train_loss 确实从 0.04 升到 0.10，说明经典 BPR 让模型"难训"。
推翻的部分：「难训 → 泛化更好」这个推论不成立。
真正解读：① user 历史只 ~7 item / 12101 items（0.06%），排除与否对负样本集合分布几乎无影响；② 但 BPR loss 对那 0.06% 的"难负样本"极敏感（neg > pos 时数值大），导致 train_loss 拉高；③ 拉高 train_loss ≠ 改善泛化——E2 的"过拟合"判断错了。

[2026-05-24] 浮点数比较用 == 而非 abs(diff)<eps（TDD 工具型踩坑）

  • 场景：写 test_bpr_loss_equals_ln2_when_equal 时用 assert bpr_loss(...).item() == math.log(2) 严格比较，结果 PyTorch float32（0.6931471824645996）vs Python double（0.6931471805599453）差 ~2e-9，测试 fail
  • 错误归属：测试 bug，不是实现 bug。实现是对的，被错误测试冤枉。
  • 根因：Claude 写浮点测试时偷懒用 ==，没有遵循"float 比较必须用容差"的常识。
  • 应对：改为 abs(a - b) < 1e-6，再跑通过。
  • agent 化提示：
    • 这正是 TDD 的额外价值——它暴露了测试本身的草率。如果先写实现再写测试，会下意识用 torch.allclose 抄过去，反而不会暴露这种思维盲点。
    • 复现型 agent 在生成测试代码时，应有 lint 规则：浮点 tensor 比较必须用 torch.allclose 或 abs(... - ...) < tol，禁 ==
    • 对偏好用 pytest.approx 的项目可以引入它，但本项目暂不引入新依赖

[2026-05-24] conda 半初始化状态：python/pip 在 PATH 但 activate 不可用

  • 场景：fingerprint 后发现 which python = ~/miniforge3/bin/python（base env），跑 conda activate fmlp-rec 报 CondaError: Run 'conda init' before 'conda activate'
  • 根因：miniforge 安装时只在 PATH 加了 miniforge3/bin，没跑 conda init zsh。结果是：
    • python / pip 命令能用（指向 base env）
    • conda 命令本身能用（base 里有）
    • 但 conda activate 是 shell function 不是真 binary，需要 conda init <shell> 写进 rc 文件才能用
  • 叠加效应：用户以为 activate 成功，pip install 装到 base env；Claude 以为环境隔离正确，进入后续阶段；TDD 跑测试才暴露。这是上一条"误判 env 激活"卡点的根因。
  • 应对：conda init zsh && source ~/.zshrc，会写一段约 14 行的 init 代码块到 ~/.zshrc。后续 activate 即可用。
  • agent 化提示：
    • "conda 装好了" ≠ "conda activate 能用"。复现型 agent 在 D15 这种"依赖隔离"决策落地后，第一件事应该是验证 activate 链路通畅（试 activate 一个临时 env），而不是直接让用户 pip install。
    • 更稳：让 agent 提供"environment fingerprint"标准命令包：which conda && conda --version && conda activate tmp && which python && conda deactivate，一键诊断 init 状态。
    • 这条和上一条合在一起，揭示 Runner / Coder agent 必须有 pre-flight env check 阶段，否则后续所有"训练失败/包找不到"都会被错误归因到代码。

[2026-05-24] 误判 conda env 已激活，导致依赖装错 env

  • 场景：用户按 D15 跑 conda create -n fmlp-rec ... && conda activate fmlp-rec && pip install -e ".[dev]"，paste 给我的输出显示 Successfully installed ... fmlp-rec-0.1.0，shell prompt 末尾是 (cuiyunlong_requirement)$。Claude 确认装好，进入后续步骤。
  • 错误表现：到 TDD 阶段 Claude 用 ~/miniforge3/envs/fmlp-rec/bin/pytest 跑测试，报 No such file or directory；pip list 显示 fmlp-rec env 内只有 pip/setuptools。之前的 pip install 实际装到了 base 或系统 Python。
  • 根因：
    1. 用户 shell prompt 里的 (cuiyunlong_requirement) 是 git 分支名（zsh git plugin 输出），不是 conda env 前缀。conda env 激活时前缀通常是 (env-name) 出现在最左侧。
    2. Claude 看到括号里有名字就默认是 conda env 激活了，从未要求 fingerprint 验证。
    3. 用户也没注意到——shell prompt 视觉上确实有歧义。
  • 应对：让用户跑 echo $CONDA_DEFAULT_ENV; which python 确认真实环境，重新 activate + 重装。
  • agent 化提示（重要）：
    • 绝不能从 shell prompt 推断 conda env 激活状态。prompt 可能被 git plugin / starship / oh-my-zsh / spaceship 等覆盖，括号里的内容来源不可信。
    • 正确做法：每次执行 env-dependent 命令前，强制 fingerprint： 
      echo "env: $CONDA_DEFAULT_ENV"
which python
which pip
    • 更进一步：复现型 agent 应当始终使用 env-bin 的绝对路径（如 ~/miniforge3/envs/fmlp-rec/bin/python）而不是依赖 PATH 解析，规避激活状态歧义。
    • 这条对未来的 Runner agent 设计是硬约束：activate 不是验证手段，which + 实际跑一个 fingerprint import 才是。

[2026-05-24] 擅自创建 README.md（违反自己的全局规则）

  • 场景：建 fmlp-rec/ 骨架时，Claude 主动写了一份 README.md，内容是「项目说明 + pipeline 跑法 + 目标指标 + 指向 journey.html 的链接」
  • 错误表现：
    1. 用户从未要求写 README，Claude 自己觉得"项目得有 README"就写了
    2. 内容大量重复 journey.html 里已经固化的 D4 / D9 / 数据集表，形成双份文档，未来必然漂移
    3. 当前 stage 任何代码都没写，README 描述的 pipeline 全是空头支票
  • 根因：Claude 的全局规则（~/.claude/CLAUDE.md 上层）明确写着 "NEVER create documentation files (*.md) or README files unless explicitly requested by the User"——规则存在但在执行流中被忽略。说明 system-prompt 级的"never"指令对长流程任务的约束力不可靠。
  • 应对：用户立即拒绝；Claude 修 pyproject.toml 去掉 readme = "README.md" 字段；这条卡点记入档案。
  • agent 化提示（重要）：
    • "禁创建 *.md 文件" 这种否定规则必须用 PreToolUse Hook 机械拦截（match Write/Edit + path 含 .md + 路径不在白名单），不能只靠 prompt
    • 更深层：Claude 有"项目仪式感"惯性——遇到新项目就想搞 README / LICENSE / CONTRIBUTING。这种惯性来自训练数据中"标准开源项目长这样"的分布偏置，对内部实验仓库是负价值，必须主动反制
    • 具体到 RecAgent：可以在 .claude/settings.json 加一条 PreToolUse Hook，匹配 fmlp-rec/**/*.md 写入直接 deny；类似规则可推广到所有 experiments/ 子项目

[2026-05-24] Read 工具读 PDF 报 pdftoppm is not installed，但 shell 里 which pdftoppm 能找到

  • 场景：用户已 brew install poppler，which pdftoppm 返回 /opt/homebrew/bin/pdftoppm，但 Claude 调 Read 读 PDF 仍报 "pdftoppm is not installed. Install poppler-utils ..."
  • 错误表现：Read 工具的子进程没继承 shell 的 PATH，找不到 /opt/homebrew/bin（macOS Apple Silicon 的 Homebrew 默认路径，不在系统 /usr/bin 里）
  • 根因猜测：Claude Code harness 中 Read 工具调用 PDF 渲染时使用的 PATH 大概率是最小化 /usr/bin:/bin，没把 brew 路径注入。这是 harness bug，不是用户配置问题。
  • 应对：放弃 Read 工具直读 PDF，改用 pdftotext -layout 经 Bash 输出到 /tmp，再 sed/grep 阅读。损失图像信息（架构图），但论文文本足够复现使用。
  • agent 化提示：
    • 复现型 agent 应在启动时检测 pdftoppm、pdftotext、git 等关键工具的可用性，报告环境缺陷而不是中途暴毙
    • 更稳妥：把 PDF 处理封装为统一接口（图像优先，失败 fallback 到文本），不依赖 harness Read 工具的隐藏行为
    • 如果将来要做 document-specialist 这种角色，PDF 处理路径必须自带 fallback 链
